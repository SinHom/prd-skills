# 产品场景构思框架

本文件在阶段三（产品方向对齐）时读取--仅当用户给的输入还很模糊、产品方向未明确时使用。方向已清晰则跳过此阶段。

目的：从碎片化业务信息中快速提炼关键洞察，输出 3~5 个结构化、可对比的场景方案，帮用户发现潜在产品机会，再收敛到单一方向进入 PRD。

---

## 场景方案输出结构

每个方案严格按以下表格输出，确保方案之间可对比、可决策：

### 场景X：[场景名称]

| 项目 | 内容 |
|------|------|
| **一句话描述** | 用一句话说清这个场景做什么 |
| **目标用户** | 谁在用？什么角色？ |
| **场景故事** | 具体使用场景（Who-When-Where-What-Why），要有画面感，让读者"看见" |
| **解决的痛点** | 对应信息摘要里的哪个痛点 |
| **核心功能** | 列出 3~5 个关键功能点 |
| **技术实现路径** | 概要技术方案，点到为止，不需要太细 |
| **预期价值** | 量化/可感知价值（效率提升X%、成本降低X%、体验提升等，无数据标 `[假设]`） |
| **实施难度** | 🟢低 / 🟡中 / 🔴高，并简要说明原因 |

### 价值-可行性矩阵（优先级建议）

所有方案出完后，用矩阵给出排序：

| 场景 | 商业价值 | 技术可行性 | 实施周期 | 推荐优先级 |
|------|---------|----------|---------|-----------|
| 场景一 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | X周/月 | 🥇 P0 强烈推荐 |
| 场景二 | ⭐⭐⭐⭐ | ⭐⭐⭐ | X周/月 | 🥈 P1 推荐 |
| 场景三 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | X周/月 | 🥉 P2 可考虑 |

附简要排序理由：为什么这样排、关键权衡点是什么。

## 构思时的核心原则

1. **强制多样性**：每个场景从不同角度切入，不要都指向同一方向。避免思维单一。
2. **场景故事要具体**：不写抽象描述，要让读者能"看见画面"--谁、在何时、何地、做什么、为什么。
3. **务实可行**：方案兼顾商业价值与技术可行性，不空谈概念，不堆 buzzword。用户导向而非炫技。
4. **信息不足主动追问**：信息严重不足（<40% 维度可确认）时，先抛 3~5 个关键问题再输出，不在关键信息缺失时强行编造。
5. **假设必标注**：所有基于推断的内容标 `[假设]`。

---

## 拓展思路（在场景方案之外主动给灵感）

完成基本场景后，主动从以下维度提供更多启发，每个维度至少给 1~2 条具体建议，不泛泛而谈：

### 1. 横向拓展（同行业）
- 同行业其他客户类型是否有类似需求？
- 能否复制到相邻细分市场？

### 2. 纵向拓展（上下游）
- 这个场景上游（供应端）和下游（消费端）还有哪些产品机会？
- 能否做成端到端解决方案？

### 3. 跨行业迁移
- 其他行业有没有已验证的类似模式？
- 可借鉴哪些成熟方案？

### 4. 技术驱动创新
- 有没有新兴技术（AI/大模型/IoT/区块链等）能创造全新场景？
- 现有场景加入新技术后能否产生质变？

### 5. 反向思考
- 如果不做这个产品，客户会怎样解决？现有替代方案最大弱点是什么？

## 场景展开（用户说「展开讲讲场景X」时）

选定某个场景后，输出该场景的详细方案，包含：

- **详细用户旅程**：端到端使用流程，每步的用户动作与系统响应
- **功能清单**：细化到功能点，标注 P0/P1/P2
- **技术架构建议**：模块划分、关键技术选型、与现有系统的关系
- **MVP 范围建议**：哪些进 MVP、哪些延后，给出理由
- **风险点**：技术、业务、合规风险及应对

展开后引导用户进入 PRD 撰写或继续调整方向。

---

## 信息摘要前置

输出场景方案前，先给出信息摘要确认理解一致：

```markdown
## 📋 信息摘要

> [3~5 句话总结关键信息]
> 明确标注：哪些是材料给出的，哪些是 [假设] 推断的

## 🎯 核心痛点分析

1. **痛点1**：描述 + 影响
2. **痛点2**：描述 + 影响
3. **痛点3**：描述 + 影响
（从用户/客户视角出发，按严重程度排序）
```

痛点是场景方案的锚--每个场景都要明确"解决哪个痛点"，否则方案就是无根的。
