## 一、产品概述

### 1.1 需求背景与目标
- **背景**：基于用户输入重构商业价值——为什么现在做、解决什么问题、不做的代价。
- **目标**：分业务目标（如 GMV/转化率/留存）与产品目标（如功能上线、覆盖场景）。目标必须可衡量，写明指标基线与目标值（无数据时标注 `[假设]`）。
- **非目标（Non-Goals）**：明确列出本期不做什么，划清边界，防止范围蔓延。

### 1.2 目标用户群体分析
按角色拆分（如：消费者、商家、运营管理员）。每个角色写：
- 画像：身份、使用场景、核心诉求
- 痛点：当前如何解决、为什么不够好
- 成功标准：对他而言"好用"的可观测信号

### 1.3 核心专业术语定义
列出本文档使用的领域术语、缩写、状态枚举，给出明确定义。目的：消除研发理解歧义。例：
- **订单（Order）**：用户发起的、含一个或多个商品的交易单元，生命周期见 3.x 订单状态机。
- **核销**：线下/履约方确认服务已交付的动作，触发订单进入"已完成"。

## 二、整体产品架构

### 2.1 核心业务流程图
用 Markdown 文本步骤描述主干链路与关键分支，确保闭环。格式：

```
用户触达 -> [分支：已登录 / 未登录]
  未登录 -> 登录/注册 -> 回到主流程
  已登录 -> 核心转化（如下单）
    -> 成功 -> 支付 -> [分支：支付成功 / 支付失败]
       支付成功 -> 履约 -> 完成（留存触达）
       支付失败 -> 失败提示 -> 回到支付
    -> 失败（如库存不足） -> 异常提示 -> 回到转化
```

关键节点标注状态变化与触发条件。每条分支都要有终态，不允许悬空。

### 2.2 功能模块脑图
列出所有一级、二级模块（含智能补全的，补全项标 `[补全]`）：

```
产品名
├── 用户体系 [补全]
│   ├── 登录注册
│   └── 权限管理
├── 核心业务模块
│   ├── ...
└── 后台管理 [补全]
    └── 数据看板
```

## 三、详细功能需求【核心】

这是 PRD 最重要部分。**每一个功能点**都必须包含以下全部子项，缺一不可：

### 功能：[功能名称]
> 例：用户手机号验证码登录

- **功能编号**：FR-XXX（便于研发追踪与测试关联）
- **用户故事**：作为 `[角色]`，我希望 `[操作]`，以便于 `[价值]`。
- **优先级**：P0 / P1 / P2（P0=必须，MVP 范围；P1=重要；P2=可延后）
- **前置条件**：例：未登录状态、网络正常、手机号合法。
- **业务逻辑/交互规则**：详细描述正向流程——用户每一步看到什么、能做什么、系统如何响应。含字段定义（名称/类型/必填/校验规则/默认值）、按钮与状态变化。
- **异常流与边缘场景（智能补全）**：见下方[异常流清单](#异常流与边缘场景清单)。例：验证码获取频繁、网络超时、验证码输入错误超限、手机号已注册/未注册、验证码过期。
- **验收标准（BDD）**：见下方[验收标准写法](#验收标准-bdd-写法规范)，用 Given/When/Then。
- **依赖与影响**：依赖哪些前置功能、会影响哪些下游模块、是否涉及数据迁移或兼容。

> 写功能时的自检：研发照着能写出接口和页面吗？测试照着能写出用例吗？回答"能"才算合格。

## PRD/HLD 边界（写 What/Why，不写 How）

PRD 描述业务实体与规则，不写技术实现。防越界正反例：

| ❌ 越界（写成 HLD 了） | ✅ 合格（PRD 该写的） |
|------------------------|----------------------|
| users 表含 id(int)、phone(varchar 11)、created_at(datetime) | 用户实体需记录手机号与注册时间 |
| POST /api/v1/login，body: {phone, code}，返回 JWT | 用户通过手机号+验证码登录，登录态需在会话内保持 |
| 用 Redis 存验证码，TTL 300s | 验证码有效期 5 分钟，过期需重新获取 |
| 前端用 Vue3 + Pinia 管理状态 | 登录态在前端会话内保持，退出后清除 |

判定标准：这是产品该决定的事，还是技术该决定的事？字段类型、表结构、接口路径、技术选型属于 HLD，业务规则、数据语义、用户可感知的行为属于 PRD。

## 四、全局与非功能性需求

### 4.1 数据埋点要求
- 核心转化漏斗埋点：列出每个关键节点的埋点事件名、触发时机、关键属性。
- 例：`order_submit`（提交订单时）属性：order_id, amount, item_count, source。
- 异常路径埋点：关键失败节点也要埋，便于漏斗分析。

### 4.2 性能与并发要求
- 响应时间：核心接口 P95 ≤ X ms。
- 并发：预估峰值 QPS / 并发用户数（无数据标 `[假设]`）。
- 数据量级：预估存储量、单表行数上限、归档策略。
- 大数据量场景：列表分页、加载更多、长列表虚拟滚动。

### 4.3 安全与风控策略
- 接口安全：鉴权方式、防重放、防爬虫限流（如验证码、滑块、IP 限频）。
- 数据安全：敏感字段脱敏/加密存储、传输加密、最小权限。
- 风控：防刷（如同一手机号验证码频率限制、设备指纹）、防薅羊毛、异常行为告警。
- 合规：如涉及个人信息，标注隐私协议、授权同意、数据留存与删除策略。

### 4.4 兼容性
- 端：Web / H5 / 小程序 / App，各端最低支持版本。
- 浏览器与分辨率、移动端机型适配范围。
- 与已有系统的兼容（旧数据、旧接口）。

## 验收标准 BDD 写法规范

验收标准用 BDD（Behavior-Driven Development）格式，每条独立、可被研发直接转测试用例：

```
**验收标准：**
- Given 用户在登录页且未登录
  When 输入合法手机号并点击"获取验证码"
  Then 60s 内收到验证码短信，按钮变为 60s 倒计时不可重复点击

- Given 已点击获取验证码
  When 60s 内再次点击
  Then 按钮不可点击，不重复发送短信

- Given 输入验证码
  When 连续输错 5 次
  Then 该手机号锁定 30 分钟，提示"尝试次数过多，请稍后再试"
```

写法要点：
- **Given**：前置状态/数据，不含动作。
- **When**：用户或系统的触发动作。
- **Then**：可观测的结果（UI 变化、数据变化、消息提示），不含实现细节。
- 一条验收标准只覆盖一个行为，复杂场景拆成多条。
- 异常流每条都要有对应验收标准。

**正反例**（验收标准必须可验证，这是同行普遍缺的约束）：

| ❌ 坏的验收标准 | ✅ 好的验收标准 |
|----------------|----------------|
| 系统正常工作 | 用户点击提交后，3秒内显示"提交成功"toast |
| 体验流畅 | 列表加载在 500ms 内完成，展示骨架屏 |
| 支持错误处理 | 输入非法手机号时，输入框下方红字提示"手机号格式错误"，提交按钮禁用 |
| 界面友好 | 验证码输入错误时，按钮变红并显示剩余尝试次数 |

判定标准：能否被测试照着写成用例？能观测、能量化、能判定对错才算合格。含"正常""流畅""友好""支持"这类形容词的一律打回重写。

## 异常流与边缘场景清单

写每个功能的"异常流与边缘场景"时，至少排查以下维度（按需取用，不是全堆上去）：

| 维度 | 典型场景 |
|------|----------|
| 输入异常 | 空值、超长、非法格式、特殊字符、边界值（0/负数/最大值） |
| 网络异常 | 超时、断网、弱网、请求重复、响应丢失 |
| 频率/限流 | 频繁点击、接口限频、验证码频控 |
| 权限/状态 | 未登录访问、无权限、资源不存在、状态不允许该操作 |
| 并发冲突 | 重复提交、库存超卖、并发编辑覆盖 |
| 数据边界 | 空列表、单条数据、海量数据、分页越界 |
| 第三方依赖 | 短信通道失败、支付回调失败、第三方接口超时/返回异常 |
| 兼容性 | 旧版本客户端、不同端表现差异 |

## PRD 内部一致性自检（v1.3 必修）

PRD 输出后未进入自检前，先做一遍"内部一致性"扫描——这是最容易漏但研发踩坑最多的维度：

1. **状态枚举全文对齐**：术语表"上下架/状态"定义的状态数（如"2 态"），对照每个 FR 的状态机描述（如"草稿/已上架/已下架 3 态"），字面必须一致
2. **同义/近义术语识别**：通读 grep 一遍"演示态/对话壳/即将上线"这类近似术语，确认是否指同一事物
3. **数据生命周期唯一性**：所有出现"保留 X 天""归档""删除"的地方，找出唯一的"真相源"位置，其他位置"对齐主条目"+指向
4. **附录/术语表与功能描述无矛盾**：术语表说"演示态 X 不支持 Y"，对应 FR 不能仍写"Y 适用"
5. **`[基础]` 模块必须展开**：所有标注 `[基础]` 的模块必须有完整 FR（用户故事 / 前置 / 业务逻辑 / 异常流 / BDD 验收），不允许"对齐基础 CRUD 模板"等一句话逃避
6. **性能数据网络值统一**：所有 `[假设]` 数值（如 P95、并发、条数）确认全文一致；如有冲突定一个"真相源"位置

把这些与 `quality-gate.md` 的六维自检连起来——一致性维度是六维之一，但如果 PRD 生成阶段不显式做这六项扫描，研发拿到手会发现各种内部硬伤。

## 输出后自检清单

PRD 输出完成前，对照自检（生成后阶段六的六维自检会复用这套，详见 `quality-gate.md`）：

- [ ] 每个功能点含全部子项（编号/故事/优先级/前置/正向逻辑/异常流/BDD验收/依赖）
- [ ] 业务流程图每条分支有终态，无死胡同
- [ ] 术语已定义，状态/字段/权限描述可编码
- [ ] 异常流按清单排查过，未遗漏关键边缘场景
- [ ] 验收标准可观测可量化，无形容词验收
- [ ] PRD 未越界写 HLD（字段类型/表结构/接口路径/技术选型）
- [ ] 埋点覆盖核心漏斗与关键失败节点
- [ ] 性能/安全/兼容性有明确指标（无数据标 `[假设]`）
- [ ] 智能补全项与遗留风险已列出
- [ ] 无"省略""TODO""参考其他模块"等偷懒表述
- [ ] **PRD 内部一致性扫描全过**（状态枚举/术语统一/数据生命周期唯一/附录无矛盾/[基础]全部展开/网络值统一）
