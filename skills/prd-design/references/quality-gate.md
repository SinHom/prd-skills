# PRD 质量门（生成后六维自检）

本文件在阶段六（生成后自检）时读取。对刚生成的 PRD 做六维度质量审查，把"生成即终稿"变成"生成->自检->迭代"闭环。方法论借鉴 nesnilnehc/review-requirements 的六维度质量门，但用作生成后自审而非独立评审（独立评审别人写的 PRD 用 `prd-review` 技能）。

## 六维度

### 1. 需求清晰度
每条需求是否无歧义、可被研发直接理解。
- [ ] 每个功能点有明确用户故事（作为X，我希望Y，以便Z）
- [ ] 术语已定义，无未定义的领域缩写
- [ ] 没有含糊措辞（"支持""大概""尽量""视情况""等"）
- [ ] 字段含义明确，无歧义命名

### 2. 可测试性
验收标准能否直接转测试用例。
- [ ] 核心功能都有 BDD 验收标准（Given/When/Then）
- [ ] 验收标准可观测、可量化（非"正常工作"这类形容词）
- [ ] 异常流每条都有对应验收标准
- [ ] 边界值场景有验收（空/满/超限/并发）
- [ ] **不能一句话逃逸**：标注 `[基础]` 或 "[对齐全量]" 的模块必须有完整 FR（用户故事 / 前置 / 业务逻辑 / 异常流 / BDD 验收）——这是 v1.3 实测教训，PRD 里"对齐基础 CRUD 模板"等一句话逃避必须打回

### 3. 约束完整性
边界、前置、异常是否覆盖。
- [ ] 每个功能有前置条件
- [ ] 异常流按 8 维度排查过（输入/网络/频率/权限/并发/数据边界/第三方/兼容）
- [ ] 状态流转有明确条件，无悬空状态
- [ ] 非功能约束有指标（性能/安全/并发，无数据标 `[假设]`）

### 4. 范围界限
Non-Goals 是否明确，防范围蔓延。
- [ ] 明确列出本期不做什么（Non-Goals）
- [ ] 功能优先级标注（P0/P1/P2）
- [ ] 智能补全项与用户原始需求区分清楚
- [ ] 没有把未来版本功能塞进当前范围
- [ ] **`[基础]` 标签须有明确子标签**（`[基础-CRUD]` / `[基础-CRUD+E]` / `[基础-CRUD+R]` 等），不允许"基础"含义模糊扩散——这是 v1.3 实测教训

### 5. 一致性与闭环
术语/状态/字段定义前后一致，流程闭环。**这是 v1.3 实测最容易跑漏的维度，重点检查**：
- [ ] 同一术语全文含义一致
- [ ] **状态枚举全文唯一**：术语表的状态定义与所有 FR 的状态机字面一致（如"上架/下架 2 态"必须全文对齐，不能在某些 FR 多出一个"草稿"）
- [ ] 每条业务流程有终态（成功/失败/异常），无死胡同
- [ ] 模块间依赖关系无环、无矛盾
- [ ] **同义/近义术语要被识别并统一**（如"演示态对话壳""对话壳""即将上线"指同一概念必须用同一术语，简称首次出现给全称）
- [ ] **数据生命周期定义唯一**：跨多次出现的生命周期数值（如"会话保留 90 天"）只能有一个真相源，其他位置"对齐主条目"+"详见 §X"而非另起定义
- [ ] **附录/术语表与功能描述无矛盾**：术语表限定某概念的能力边界后，对应 FR 不能仍写超出边界的特性

### 6. 开放问题与风险
遗留假设是否标注，待确认项是否列出。
- [ ] 所有 `[假设]` 已列出
- [ ] 待确认问题集中列出（第五章遗留风险）
- [ ] 风险点附影响与建议处理
- [ ] 没有未说明的 TODO/省略

## findings 输出格式

自检发现的问题用表格输出，便于定位修复：

| 维度 | 位置 | 严重性 | 问题 | 修复建议 |
|------|------|--------|------|----------|
| 可测试性 | 3.2 订单功能-验收标准 | critical | 缺"库存不足"异常流验收 | 补 Given 库存为0 When 下单 Then 提示"库存不足"且订单不创建 |
| 范围界限 | 1.1 目标 | major | 未列 Non-Goals | 补"本期不做售后退款"等边界 |

## 严重性分级

- **critical**：不修无法开发或有逻辑硬伤（流程死胡同、验收缺失、核心矛盾）。**必须当场修后再交付。**
- **major**：影响开发质量或漏关键场景（异常流不全、Non-Goals 缺失）。**必须当场修。**
- **minor**：优化项（措辞不清、建议补图）。标注后留给用户决定。
- **suggestion**：锦上添花。可选。

---

## 自检流程

1. 按 1→6 顺序逐维度过，每个维度对照检查项打勾/标问题。
2. 汇总 findings，按严重性排序（critical→major→minor→suggestion）。
3. critical/major 当场修复 PRD，修完在 findings 标"已修"。
4. minor/suggestion 列出留给用户。
5. 输出结论：`✅ 已通过六维自检，修复 critical/major X 处，遗留 minor N 处、suggestion M 处。`

自检视角：切换成**陌生研发视角**——假设你是第一次见这份 PRD、要照着开发的工程师。看不懂、没法测、没法做的就是问题。刨子和尺子不能握在同一只手里：生成 PRD 的视角不能同时负责"评"。
