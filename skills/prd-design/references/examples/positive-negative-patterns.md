# PRD 正反例集中

> 所有 v1.3 实测中识别出的"好的 / 坏的"PRD 写法集中。每项配 1-2 句解释，方便新人/未来对照。
> 这是 prd-template 和 quality-gate 里散落的正反例的合并版，**一处查所有**。

---

## 1. 验收标准（BDD）

| ❌ 不可测 | ✅ 可测 |
|----------|---------|
| "系统正常工作" | "用户点击提交后 3 秒内显示'提交成功'toast" |
| "体验流畅" | "列表 500ms 内加载并展示骨架屏" |
| "支持错误处理" | "输入非法手机号时输入框红字提示，按钮禁用" |
| "界面友好" | "验证码输入错误时按钮变红并显示剩余尝试次数" |

**判定标准**：能否被测试照着写成用例？可观测 + 能量化 + 能判定对错才算合格。
**禁用**："正常""流畅""友好""支持"等形容词一律打回重写。

---

## 2. PRD/HLD 边界

| ❌ 越界（写成 HLD 了） | ✅ 合格（PRD 该写的） |
|------------------------|----------------------|
| users 表含 id(int)、phone(varchar 11)、created_at(datetime) | 用户实体需记录手机号与注册时间 |
| POST /api/v1/login，body: {phone, code}，返回 JWT | 用户通过手机号+验证码登录，登录态需在会话内保持 |
| 用 Redis 存验证码，TTL 300s | 验证码有效期 5 分钟，过期需重新获取 |
| 前端用 Vue3 + Pinia 管理状态 | 登录态在前端会话内保持，退出后清除 |

**判定标准**：这是产品该决定还是技术该决定？字段类型/表结构/接口路径/技术选型属 HLD，业务规则/数据语义/用户可感知行为属 PRD。

---

## 3. 状态机

| ❌ 模糊 | ✅ 精确 |
|--------|--------|
| 术语表说"上架/下架 2 态" | 术语表定义 + 每个 FR 引用都字面一致 |
| FR 业务逻辑说"草稿/已上架/已下架 3 态" | 全文统一一处定义（消除术语表与 FR 状态机字面冲突） |
| "在适当的时候状态变更" | 完整状态枚举 + 流转条件 |
| 状态变更"系统内部"还是"用户可见"模糊 | 显式标"系统内部过渡态，运营方不感知" |

**判定标准**：状态枚举在术语表与 FR 间字面 grep 一致；不能某 FR 多出一个状态。
**v1.3 实测教训**：状态机 3 态 vs 2 态自相矛盾是最隐蔽的 critical 一致性问题，研发拿到 PRD 后直接卡死。

---

## 4. 术语

| ❌ 同义混用 | ✅ 统一 |
|----------|---------|
| "演示态对话壳""即将上线""对话壳"三个说法指同一概念 | 选定"演示态对话壳"统一术语，首次出现给全称 |
| "工单""任务""ticket"全文混用 | 全文用同一词 |
| 一术语两处定义不一致 | 术语表是唯一真相源 |

**判定标准**：同义/近义术语要识别并统一；术语表是真相源。
**v1.3 实测教训**：PRD 里三个近似术语散落，主流程读起来松散，研发反复 check。

---

## 5. 数据生命周期

| ❌ 多次定义 | ✅ 单一真相源 |
|----------|----------|
| "会话保留 90 天"（A6）+ "数据 90 天后归档"（4.2）+ "90 天 + 删除机制"（4.3）+ "默认 90 天"（F4），四散各自定义 | 一处定义（FR-A6）：**"90 天内可查询 → 90 天后归档（不可查询但加密保留）→ 超过 365 天物理删除"** |
| 其他位置另起定义 | 其他位置"对齐 FR-A6"或"详见 §X"，不另起定义 |

**判定标准**：生命周期数值（天数、归档/删除）跨多次出现只能有一处真值；其他位置只引用。

## 6. [基础] 标签

| ❌ 偷懒 | ✅ 展开 |
|--------|--------|
| "[基础] 列表 + 详情 + 基础 CRUD" 一句话 | 完整 FR（用户故事/前置/业务逻辑/异常流/BDD 验收/依赖） |
| 一句话覆盖 N 个不同模块 | 明确子标签 `[基础-CRUD]` / `[基础-CRUD+E]` / `[基础-CRUD+R]` |
| "对齐基础 CRUD 模板""详见 FR-B1 模板"逃避 | 必须独立写完整 FR——**研发无完整 FR 就无实施边界** |

**判定标准**：[基础] 是约束（"做最小可用"），**不是省略依据**。每个 `[基础]` 模块必须有完整 FR。
**v1.3 实测教训**：PRD 里 §E 6 个模块用一句话逃避，研发拿不到实施边界，会反复回头加需求。

## 7. PRD 一致性扫描清单（生成后必过）

每份 PRD 输出后跑一遍下列 grep/scan，每条不通过 = 一次"self-debug 循环"，直到全部清零才能进交付：

1. **状态枚举全文 grep**——有且只有术语表那一个版本
   - 命令：`grep '草稿.*上架\|上架.*下架'`等检查状态混用
2. **同义术语识别**——N 个说法指同一事物必须合并
   - 命令：`grep "演示态\|对话壳\|即将上线"`
3. **数据生命周期 grep**——唯一真相源位置已标记
   - 命令：`grep "90 天\|归档\|删除"`
4. **附录/术语表 vs 功能描述 grep**——不能矛盾
5. **[基础] 模块 grep**——必须有完整 FR
   - 命令：`grep "对齐.*基础\|对齐.*模板"`
6. **性能等假设数值 grep**——全文一致
   - 命令：`grep "P95\|QPS\|ms"`

每条不通过 = 一次重写或回归。**全部清零才能进阶段六自检**。

## 8. 反例补充：什么时候需要打回重写

| 场景 | 行动 |
|------|------|
| 验收标准含反例 1-4 任意一个 | 打回重写 |
| 状态机、术语、数据生命周期有内部矛盾 | 打回重写 |
| [基础] 模块一句话逃避 | 打回重写 |
| PRD 字段定义含 HLD 细节（vachar、N 表） | 移到 HLD 文档，PRD 留语义 |
| "支持一切""全自动"大词 | 打回重写 |
| TODO/省略/"参考其他模块" | 当场补或显式标为遗留风险 |
| 流程图缺重要分支 | 补 |
| `[假设]` 关键指标无说明 | 标决策负责人 |

**原则**：发现的当下打回最便宜；带着错误进阶段六自检越晚修越贵。
