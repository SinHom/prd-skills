## 补全原则

1. **补行业标准必备，不补锦上添花**。目的是闭环和防漏，不是堆功能。
2. **每项补全都要说理由**：为什么这个产品必须有它、不补会出什么问题。
3. **按产品类型匹配**：先识别产品属于哪类（可能跨类，如"医疗 + B 端 SaaS"），各取所需。
4. **标注优先级**：P0（必须，MVP）/ P1（重要）/ P2（可延后），帮用户判断范围。
5. **不替用户做商业决策**：补全的是"技术/体验/合规层面绕不开的"，不是"商业模式上可以加的"。

## 通用基础模块（所有产品都要查）

无论什么产品，先核对这些是否覆盖。这是体验闭环与合规的地基：

| 模块 | 为什么必须有 | 优先级 |
|------|-------------|--------|
| 登录注册 / 身份认证 | 任何需要识别用户的产品都要有身份基础 | P0 |
| 权限控制 | 区分普通用户/管理员/不同角色可见范围 | P0/P1 |
| 用户协议与隐私授权 | 上线合规前置条件 | P0 |
| 空状态 | 列表/详情无数据时的引导，避免"白屏" | P1 |
| 加载态 | 异步请求时的 loading 反馈 | P1 |
| 网络异常处理 | 断网/超时/失败时的提示与重试 | P1 |
| 数据校验 | 前端即时校验 + 后端校验，防脏数据 | P0 |
| 错误提示体系 | 统一的错误码与文案规范 | P1 |
| 分页 / 加载更多 | 任何列表类数据都要有翻页或滚动加载 | P1 |
| 操作反馈 | 成功/失败/进行中的 toast 或状态变化 | P1 |
| 退出登录 | 会话结束入口 | P1 |

## 电商/交易类

涉及下单、交易、履约的产品。

| 模块 | 补全理由 |
|------|---------|
| 商品状态机 | 上架/下架/售罄，避免展示不可售商品 |
| 购物车 | 多商品合并下单的基础 |
| 订单状态机 | 待支付/已支付/待发货/已发货/已完成/已取消/已退款--每态明确流转条件 |
| 库存管理 | 下单扣减、取消回补、并发防超卖 |
| 退款逆向流程 | 退款申请->审核->退款->退库存，与正向订单对齐 |
| 优惠券/促销 | 满减/折扣/叠加规则、有效期、使用范围 |
| 收货地址管理 | 默认地址、增删改、校验 |
| 支付方式选择 | 多渠道（微信/支付宝等）、支付超时关单 |
| 物流跟踪 | 履约状态同步 |
| 售后/评价 | 交易闭环后的反馈与售后入口 |
| 价格展示规则 | 划线价/到手价/税费/运费分离展示 |

## 非功能性补全清单

无论什么产品，最终都要确认这些维度有明确要求（无数据标 `[假设]`）：

| 维度 | 补全要点 |
|------|---------|
| 性能 | 核心接口响应时间（P95）、首屏加载、列表渲染 |
| 并发 | 峰值 QPS、并发用户数预估 |
| 安全 | 鉴权、接口防刷、敏感数据加密、传输安全 |
| 可用性 | SLA 目标、降级策略、监控告警 |
| 兼容性 | 端/浏览器/分辨率/旧版本兼容范围 |
| 可扩展 | 数据归档、水平扩展预留、接口版本化 |
| 合规 | 隐私协议、数据留存与删除、备案（如需 ICP/算法备案） |
| 埋点 | 核心漏斗与关键失败节点的数据采集 |

> 用法：识别产品类型后，取对应行业表 + 通用基础表 + 非功能性清单，逐项判断"用户材料里有没有覆盖"，缺失的就是补全候选。
