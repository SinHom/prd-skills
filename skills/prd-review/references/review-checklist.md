## 维度1：需求清晰度
每条需求是否无歧义、可被研发直接理解。

检查项：
- [ ] 每个功能点有用户故事（作为X，我希望Y，以便Z）
- [ ] 目标用户画像清晰，非"所有用户"
- [ ] 术语已定义，无未定义的领域缩写
- [ ] 无含糊措辞（"支持""大概""尽量""视情况""等"）
- [ ] 字段含义明确，命名无歧义
- [ ] 业务规则有明确触发条件，非"在适当的时候"

典型问题（->严重性）：
- 验收标准写"系统正常工作" -> critical（无法验收）
- "支持多种登录方式"未列明哪些 -> major
- 术语"工单"全文未定义就直接用 -> major

---

## 维度2：可测试性
验收标准能否直接转测试用例。

检查项：
- [ ] 核心功能都有 BDD 验收标准（Given/When/Then）
- [ ] 验收标准可观测、可量化，非形容词
- [ ] 异常流每条都有对应验收标准
- [ ] 边界值场景有验收（空/满/超限/并发/0/负数）
- [ ] 状态变化有可观测信号（UI/数据/消息）
- [ ] 没有用"流畅""友好""正常"这类不可测词

正反例参考：

| ❌ 不可测 | ✅ 可测 |
|----------|---------|
| 体验流畅 | 列表 500ms 内加载，展示骨架屏 |
| 支持错误处理 | 输入非法手机号时红字提示，提交禁用 |

典型问题：
- 核心功能无验收标准 -> critical
- 验收标准含形容词不可测 -> major
- 异常流缺验收 -> major

---

## 维度3：约束完整性
边界、前置、异常是否覆盖。

检查项：
- [ ] 每个功能有前置条件
- [ ] 异常流按 8 维度排查：输入异常/网络异常/频率限流/权限状态/并发冲突/数据边界/第三方依赖/兼容性
- [ ] 状态流转有明确条件，无悬空状态
- [ ] 非功能约束有指标（性能 P95、并发 QPS、安全），无数据标 `[假设]`
- [ ] 权限边界明确（谁能看/能操作什么）
- [ ] 数据校验规则完整（前端+后端）

典型问题：
- 核心流程无异常流 -> critical
- 缺并发场景（如库存超卖、重复提交） -> major
- 性能要求缺失 -> major
- 未提数据校验 -> minor

---

## 维度4：范围界限
Non-Goals 是否明确，防范围蔓延。

检查项：
- [ ] 明确列出本期不做（Non-Goals）
- [ ] 功能优先级标注（P0/P1/P2）
- [ ] 智能补全项与原始需求区分
- [ ] 没有把未来版本塞进当前
- [ ] 需求边界与相关系统职责划分清楚
- [ ] 没有"支持一切""全自动"这类大词

典型问题：
- 无 Non-Goals，范围无边界 -> major
- 把"未来支持AI推荐"写进当前 -> major
- "支持所有支付方式"不可信大词 -> major

## 维度5：一致性与闭环（含中间地带观察层）
术语/状态/字段前后一致，流程闭环。

> **观察层 C · 中间地带**（v1.2 新增）：本维度同时承载"逻辑层 B"和"中间地带 C"两类观察。审查时两类都走——只走 B 会漏掉流程闭合/前置锁/数据生命周期/附录一致性等问题（v1.2 实战占每次 finding 20%+）。

**中间地带四大检查点**：
- **流程闭合**：每个 FR 看自己闭环吗？跨 FR 依赖有无悬空？
- **前置锁**：关键表单/触发是否有前置约束（项目状态/资质审批/必填字段）？
- **数据生命周期**：留存/归档/删除跨多少处定义？有几个真相源？
- **附录一致性**：术语表与 FR 字面是否一致？

检查项：
- [ ] 同一术语全文含义一致
- [ ] **状态枚举全文唯一**：所有 FR 中的状态机与术语表的"状态定义"字面一致；草稿/上架/下架这类字段不能在不同 FR 出现不同枚举值
- [ ] 每条业务流程有终态（成功/失败/异常），无死胡同
- [ ] 模块间依赖无环、无矛盾
- [ ] 数据流向清晰（数据从哪来、到哪去、谁可改）
- [ ] 前后端职责划分一致
- [ ] **同一概念的多个同义/近义术语要被识别并统一**（如"演示态对话壳""对话壳""即将上线"指同一事物）
- [ ] **数据生命周期定义唯一**（如"会话保留 90 天"这类数值，PRD 内只能有一个真相源；其他位置引用它而非另起定义）
- [ ] **附录/术语表与功能描述无矛盾**：术语表说"演示态 X 不支持 Y"，对应 FR 不能仍写"Y 适用"

典型问题：
- 流程到某步无终态 -> critical（死胡同）
- "订单状态"在两处定义不一致 -> critical（**这是 PRD 内部硬伤，研发无所适从**）
- 术语前后矛盾 -> major
- "演示态对话壳"与"即将上线"与"对话壳"指同一概念但分开用，主流程读起来散 -> major

## 维度6：开放问题与风险
遗留假设、待确认项、风险是否标注。

检查项：
- [ ] 所有假设已显式标注（`[假设]`）
- [ ] 待确认问题集中列出
- [ ] 风险点附影响与建议处理
- [ ] 无未说明的 TODO/省略/"参考其他文档"
- [ ] 依赖项明确（依赖哪些前置/外部系统）
- [ ] 合规风险标注（隐私/数据安全）

典型问题：
- 大段假设未标注 -> major
- 残留 TODO/省略 -> major
- 未标合规风险（涉个人信息） -> major

## 严重性判定标准

| 严重性 | 判定 | 处理 |
|--------|------|------|
| 🔴 critical | 不修无法开发 / 逻辑硬伤 / 流程死胡同 / 验收缺失 / 核心矛盾 | 必须修后才能交付 |
| 🟠 major | 影响开发质量 / 漏关键场景 / 范围不清 | 必须修 |
| 🟡 minor | 优化项 / 措辞不清 / 建议补图 | 建议修，可后置 |
| 🔵 suggestion | 锦上添花 | 可选 |

判定原则：照这份 PRD，研发会不会卡住或返工？会=至少 major；完全没法做=critical。

## 典型问题速查

审查时高频出现的问题，快速对照：

| 症状 | 常见维度 | 常见严重性 |
|------|---------|-----------|
| 验收标准含"正常/流畅/友好" | 可测试性 | major |
| 核心功能无验收标准 | 可测试性 | critical |
| 流程到某步没下文 | 一致性与闭环 | critical |
| 异常流只写"网络异常"四个字 | 约束完整性 | major |
| 无 Non-Goals | 范围界限 | major |
| 假设混在正文里没标注 | 开放问题 | major |
| 术语前后定义不一致 | 一致性与闭环 | critical |
| 缺并发/超卖场景 | 约束完整性 | major |
| 性能指标缺失 | 约束完整性 | major |
| 残留 TODO/省略 | 开放问题 | major |
